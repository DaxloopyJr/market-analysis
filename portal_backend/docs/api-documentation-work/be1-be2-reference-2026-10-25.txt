Viwanda Portal BE1 and BE2 API Reference
Current implementation reference 25 October 2026
This reference covers all registered application API routes in the current Laravel backend for frontend integration and Postman testing. It documents 123 method/path entries: the registered submissions action route is expanded into review, approve, return and publish. GET aliases for HEAD are not counted separately. The archived tab is historical; use this tab for current integration.
Scope and request conventions
Use {{baseUrl}} = <your deployed origin>/api/v1. Append endpoint paths below to this base URL. /api/health is an absolute compatibility path from the origin. Framework /up and Sanctum CSRF-cookie routes are not application JSON API entries here.
Headers: Accept: application/json. Protected routes require Authorization: Bearer <token>. JSON writes use Content-Type: application/json. Logo upload uses multipart form-data with a client-generated boundary and _method=PUT. Authentication and public portal settings do not need a token.
Examples use illustrative IDs, dates and selected response fields; they are not live database records or exhaustive JSON schemas. Replace IDs with responses from the fresh environment. Schematics such as {data:User} name the returned record type and are not literal JSON. Do not hardcode workflow IDs from old testing sessions.
General errors: 401 unauthenticated; 403 forbidden/inactive/wrong role or assignment; 404 nonexistent or invisible resource; 409 duplicate/state/revision/reviewer conflict; 422 validation; 502 configured email/SMS transport failure where documented. Unexpected infrastructure errors can return500. Error bodies usually contain message; validation adds errors keyed by field. Success bodies vary by module and are shown per endpoint.
Pagination: most dataset/reporting/submission lists return a root paginator {current_page,data,per_page,total,...}. Administration lists wrap the paginator inside {status:'success',data:{current_page,data,...}}, so rows are data.data. Audit and notifications use resource-style data/links/meta. Workflow lists and eligible-officers return unpaginated data arrays. Default20,max100 only where perPage is supported.
Role and scope rules
BE1 ownership: authentication, accounts, RBAC, institution/department administration, delegations, workflow configuration and submissions. BE2 ownership: dataset configuration, consumers metadata, periods/calendars, targets, dashboard, audit and portal settings. Notifications and search are integration surfaces; ownership labels do not change API permissions.
MOA operates across organisations. IA manages its own institution. IDO works within its institution; DDO within MIT and its department. Dataset configuration scope and submission edit scope differ: saving/submitting requires the eligible officer assigned to the calendar. MDO and MDD must belong to active MIT and serve all source institutions/departments at ministry stage; no per-source M&E assignment filtering. Other workflow roles retain policy scope checks. Explicit step assignments, where supported, are enforced.
Frontend must render submission action buttons from data.allowedActions, not role names alone. Values are save,submit,review,approve,return,publish,correct. Each action request must also pass server authorization. Source officers cannot review their own submissions.
Current workflow and version behaviour
Default institution: IDO submits -> IHOD review -> AO approve -> ministry. Default department: DDO submits -> ministry. Default ministry: MDO review -> MDD publish. can_return:true provides return at review/publication stages. Separate ministry approve is optional; if configured, it precedes the single final publish. Ministry requires at least two stages; publish-only is invalid. Institution ends approve and cannot publish.
MDO review moving to publish sets stored status approved, meaning ready for publication; it does not invent an MDD approve event. MDD then sees publish and return. Publication sets publishedAt/status published and clears currentStep.
The currently assigned reviewer finishes the pending stage. A forward transition then selects the active workflow version and maps progress by level,role,action and current-attempt history. It does not go from approval back to review or repeat completed stages. Ambiguous repeated role/action pairs across versions return409. The current workflow is not silently rewritten merely by opening a GET. Legacy null-stage paths remain pinned. Returns restart the last selected initial path on resubmission.
Template migration is separate: new dataset activation adopts the latest form only for never-submitted drafts and eligible calendars/targets. Original form/values are archived before dropped fields are removed. Compatible values retained; new fields may require entry; revision increments. Submitted/returned/under-review/approved/published records retain their template. Render each submission using its own returned template and values.
Submission integration sequence
1. Fetch/select the dataset and shared reporting period. GET dataset submission-status immediately; show reason and existing submissionId when blocked/view. A read here does not create a calendar or draft.
2. If start/resume is allowed, POST submission-context with startYear,frequency,periodNumber (omit periodNumber for annual). Read reportingCalendarId,templateVersionId,template and targets.
3. POST /submissions with reportingCalendarId to start/reuse the draft. PUT /submissions/{id}/values with expectedRevision equal to current data.revision. POST submit with the updated revision.
4. Reviewers GET the submission with their own token, use allowedActions and post the corresponding action. After each response refresh revision/currentStep/actions. On409 reread before retrying; do not increment revision manually.
5. IHOD corrections use PATCH values with reason and expectedRevision. Return requires comments plus correctionDeadline; the responsible officer saves corrections and resubmits. In-app notifications record handoffs/corrections; workflow email delivery is not implemented.
Values and targets
Summary rows use value plus breakdowns[{dimensionId,optionId,value}] and optional remarks. Cross-tab rows use dimensionValues[{dimensionId,value}] plus value. Do not mix summary and cross-tab shapes for one indicator. Numeric decimal values must be strings. Each filled/required breakdown dimension independently totals the indicator value; Gender and Staff Category are not summed together. Entirely omitted optional dimensions remain valid.
Targets are optional planning values per dataset,indicator,period and optional dimension combination. targetScope total is the indicator total for that period, not automatically an annual total. Q1/Q2/new-year targets are separate records; no automatic copying/allocation or total-versus-dimension-target sum check. Actual submission values need not equal targets. Targets may be created on draft or active datasets; template/period validation applies. Current target update is not automatically blocked by an existing submitted record.
Data Consumers are descriptive dataset metadata in this phase. Attaching/removing a consumer does not create a login, role, permission or data-access grant.
Operational limits and readiness
Scheduler must run for automatic period synchronization and reminders. Period dates use Africa/Dar_es_Salaam; manual closure overrides normal windows, while an automatically expired parent need not block an otherwise valid child/correction window. New reporting years and targets do not require editing the dataset master.
GET /search is registered but references legacy data models/relations and may return500; its intended response is documented as such. Standalone institution analytics, report/PDF/Excel export and GovESB endpoints are not implemented in the current route inventory. Menu/permission entries for those features do not create APIs.
This is code-grounded documentation, not a claim that every endpoint has been exercised against production. Examples are selective; use the authoritative response and current template IDs. No database reset, application-code changes, API mutations or messages to users were performed to prepare this reference.
