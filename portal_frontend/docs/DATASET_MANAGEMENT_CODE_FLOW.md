**Scope:** Dataset Management only. **Route:** `/dashboard/datasets`  
**Approved UI source:** `VIWANDA_DATASET_MANAGEMENT_UIUX_REVIEW(1).zip` supplied and approved by the user.  
**Source of truth:** remote Laravel API `/api/v1`, not local mock records.  
**Permissions:** MOA/IA/IDO/DDO are listed in the supplied dataset contract; backend enforces institution/department scope D.

## 2. User flow: dataset wizard

1. **Basic Information:** Name, description, institution source selector, free-text source description, SECTOR/subsector (from Reference Management), consumers (search existing or type a new name, multi-select), frequencies, Method: Portal (`manual`) or System (`system`; requires `sourceSystemName`), Priority shown as High policy hint (not POSTed). There are **NO Sections** and **NO Input/Output Type**. `datasetCode` is generated by Laravel only.
2. **Reporting & Assignment:** choose/reuse reporting periods and assign one eligible IDO/DDO responsible officer **per dataset-period**. `GET/PUT /datasets/{id}/reporting-calendar`, `GET/POST /reporting-periods`, `POST /reporting-periods/{id}/quarters`. `submittedAt` and deadline are not client-submitted.
3. **Indicators & Dimensions:** attach/create indicator with `integer`, `decimal`, `text`, `boolean`, `date`; numeric indicators may refer to active UNIT values from Reference Management. Optional dimension name plus manually entered **option labels** are created via `POST /datasets/{id}/dimensions`. Actual values (`Academic Staff = 10`) belong to Data Entry, **not** dataset configuration.
4. **Review & Activate:** `GET /datasets/{id}/configuration-progress`; `POST /datasets/{id}/activate`. `POST /datasets/{id}/draft` reopens for editing. `GET /datasets/{id}/template-versions` shows immutable versions. Historical data remains tied to its original version.

## 4. Save & Next correction

**Previous problem:** `Save & Next` waited for 7 post-save dependent requests (periods, users, indicators, versions, etc.), and then waited for a success alert to be dismissed before moving forward. Failed secondary reads could be mistaken for a failed create. Repeated clicks risked additional POSTs.

**Corrected sequence:**

```text
Save & Next click
  → validateDatasetBasic(form)       → visible field/summary errors if incomplete
  → saveGate prevents concurrent POST
  → POST /datasets OR PATCH /datasets/{id} (only supported payload fields)
  → retain Laravel-returned dataset ID
  → setStep(1) immediately upon successful write
  → nonblocking success toast, server message preserved
  → background loadDataset(id) for secondary records
  → if background reads fail: visible warning, do not lose saved ID, do not repeat POST
```

The **Next** buttons on subsequent steps advance locally; final activation is decided by `configuration-progress` and Laravel validation. Moving to a step does not mean the dataset is activated.

## 5. Submission-style wizard completion ticks (Add AND Edit)

`src/pages/ModulePage/datasetFormRules.js` exports `datasetWizardCompletion()` and the dataset page calls it via `useMemo`.
The four steppers render a green `CheckCircle2` when Laravel-backed completion is true.
Merely opening a step, clicking Next, or selecting a tab **does not produce a tick**.

| Step | When the tick appears | How it updates |
|---|---|---|
| Basic Information | Laravel POST/PATCH succeeded and an actual dataset ID exists | `saveBasic` commits the server response; reopening loads persisted data |
| Reporting & Assignment | `configuration-progress.steps.reportingPlan.complete === true` | After `PUT /datasets/{id}/reporting-calendar`, refresh progress asynchronously |
| Indicators & Dimensions | `configuration-progress.steps.indicatorsAndDimensions.complete === true` | After indicator add/edit/detach, refresh progress asynchronously |
| Review & Activate | Backend dataset status is `active` after successful activation | `ReviewStep.activate` -> `loadDataset` -> current status |

If the progress endpoint hasn't loaded, the stepper can temporarily infer a saved assignment/indicator from
*server-fetched* lists. If Laravel explicitly reports `complete:false`, that verdict overrides the fallback.
Reopening for a new version returns status to `draft`, clearing only the final tick while previous snapshots stay safe.
Any 403/422/failed write will not mark a step complete, and Next remains independent of the stepper indicators.

## 6. Reference Management dependency

`src/API/referenceData.jsx`: `getActiveReferenceOptions("SECTOR")` and `getActiveReferenceOptions("UNIT")`. The function resolves the reference type by `data_type_code`, paginates the type-specific values, and excludes inactive/not-yet-effective/expired values. `parentId` allows sector/subsector nesting. If the backend lacks an active `SECTOR` type, Dataset creation shows an error rather than fake options.

## 7. Backend contract restrictions requiring decisions

- **Ministry-only source:** `POST /datasets` requires `institutionId`; supplied contract did not define the actual Ministry mapping. Do not invent an ID. This selector displays the missing mapping clearly until backend confirms one.
- **Priority:** The supplied POST schema does not accept priority, and `/datasets/{id}/priority` is MDO-only and cannot set first priority. The approved UI displays High as the default *policy*, not a falsely persisted value. First priority requires backend review-process support.
- **Source level:** UI maps Portal to `manual` and System to `system`. A free-text `sourceDescription` is sent for both.
- **Sections and Input/Output Type:** removed by agreement, not sent.
- **Editing manual dimension options:** creation supported; modification of existing option records is not exposed in this contract.
- **Officer eligibility:** `GET /users` might be unavailable to IDO/DDO. A scoped officer-lookup endpoint or backend permission change is needed if that happens; do not hardcode options.
- **Actual data-entry values/remarks:** out of this module and not saved with targets. Requires Data Entry / Submission contract later.

## 2026-10-21 — Source Level → Backend Institution / Ministry Department

**UI reference:** Approved Dataset Management UI, unchanged except that the source selector is conditional.

**Institution**: `Source Level = Institution` → a select populated by `GET /api/v1/institutions` (`src/API/institution.jsx`); the selected ID goes to `institutionId`, with `departmentId: null`.

**Ministry**: `Source Level = Ministry` → a select populated by `GET /api/v1/departments` (`src/API/department.jsx`); the selected ID goes to `departmentId`, with `institutionId: null`. Dropdown labels show names and optional codes, all from real Laravel responses. Source Level changes clear previously selected IDs. No hardcoded institution/department records.

**Data Source Description** (`sourceDescription`) remains a manual free-text input for either selection, e.g. `Research Unit`, `ICT Team` or `Trade Promotion Desk`. It does **not** use the department dropdown: the dropdown is the organizational owner; description is the detailed data-origin narrative.

**Code flow:** `src/pages/ModulePage/Datasets.jsx` → `src/utils/datasetSource.js` and `src/pages/ModulePage/datasetFormRules.js` → `src/API/dataset.jsx` → `src/API/axios.jsx` → remote Laravel `/api/v1/datasets` → PostgreSQL. Each file has a header comment describing the route/connection.

**Important backend limitations (do not fabricate a workaround):**

1. The provided `POST /datasets` contract includes `departmentId` but **requires** `institutionId`. Ministry creation sends the selected real `departmentId` with `institutionId: null`; Laravel may currently reject it with 422. Backend should clarify conditional ownership, e.g. allow a ministry-level department ID instead of an institution ID, or return an authoritative mapping. We have neither fabricated nor hardcoded a ministry ID.
2. The supplied `GET /departments` endpoint is permission-gated by `departments.manage` (MOA). IA / IDO / DDO may receive 403 if they select Ministry. The page displays that permission error; backend may need a scoped read-only department-options contract.
3. The `PATCH /datasets/{id}` contract explicitly states institution and department are immutable. Source Level and its owner select are therefore **read-only in Edit**, avoiding the appearance of a save that Laravel would silently ignore. A new dataset is needed to switch organizational ownership until a supported backend change exists.
4. The Reporting Calendar examples are institution-scoped and expect `institutionId` on reporting periods; support for Ministry department-only reporting calendars is not documented. The UI explains the limitation without inventing a calendar API.
